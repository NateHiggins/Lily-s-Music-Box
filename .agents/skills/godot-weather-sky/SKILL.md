# Weather and sky through their actual owners

Improve the requested atmosphere while preserving the campaign, geographic,
lighting and gameplay authorities. Distinguish an editable control, a rendered
effect, a technically qualified behavior and the owner's artistic acceptance.
No finite gallery establishes perfect behavior across every configuration.

Use [Godot development](../godot-development/SKILL.md) for implementation,
execution and evidence, and [textures and shaders](../godot-textures-and-shaders/SKILL.md)
for appearance, resources and performance. Follow [DOCS.md](../../../DOCS.md)
and its Bible precedence. This skill adds the weather-specific ownership,
configuration and verification decisions rather than another engine manual.

## Select the relevant reference

- Read [architecture and controls](references/architecture-and-controls.md)
  before changing an owner, unit conversion, shader default or exposed control.
  Trace the loaded shader and all setters; a declaration alone is not a working
  control. The project's normal Forward+ path is **queens_weather_sky**, while
  **v2_seasonal_sky** is the explicit comparison baseline.
- Read [configuration and recipes](references/configuration-and-recipes.md)
  when building a weather state, extending the data grammar or designing a
  comparison. Preserve the difference between supported runtime input, a debug
  override and a proposed authoring recipe.
- Read [verification](references/verification.md) before claiming improved
  appearance, deterministic motion, coverage, performance or production use.
  Choose cases for the changed mechanism and its nearest interactions, then
  extend coverage only where the evidence warrants it.

## Carry the change through

Identify the concrete defect or requested look and the smallest missing witness.
Record the actual renderer, shader/include stack, source mode, date/observer,
seed, quality settings and final bound values. Inspect the current code when an
older weather document describes a retained implementation rather than V2.

Change a parameter at its maintained owner. Preserve normalized weather facts,
single Environment/key-light ownership, exposure/cover queries and existing
resource lifetimes. When a hard-coded expression needs a real control, define
its type, unit, permitted range, default, binder, invalid-input behavior and
verification before wiring it through; do not scatter another set of constants.

Make source/data checks first, then inspect the effect in the actual production
composition, including motion and transitions. Compare equivalent camera and
quality settings; separate compile/startup cost, warmed rendering and fast time
traversal. Keep changed-input evidence separate from reusable unchanged checks.

Weather and astronomy consume authoritative campaign time and the existing
observer. Preserve the prologue's borrowed month/day/time within its historical
annual loop, monotonic elapsed/deadline clocks, render-only sky traversal and
the protected destination/ending. A sky improvement does not authorize modern
calendar substitution, location inference, new forecasts, narrative events,
extra clocks, lights, network services or save domains.

Deliver named changes, the controls actually exposed, tested combinations,
source-bound evidence, observed cost and remaining gaps. Keep unsupported or
unrendered configurations explicit rather than describing the whole system as
finished.
